# Pico Assets upload source composition

This private continuation adds the fourth normal Assets action, glTF bundle
Upload, to the existing baseline/Open/picker/Cancel owner. It does not complete
the 29-action Common journey, independent Actor/Model/bake/render proof, or
whole-feature retirement. Native producer instrumentation is source-only and
has not been compiled or run on an AssetServer or Pico.

## Existing ownership and limits

The default factory with `backend=None` still creates Prefix2/Layout1. An
explicit fresh `PicoAssetsBackendOriginals` selects Prefix3/Layout2 and
`assetsWireOriginalLayoutVersion: 1`; the actual binding creates the same
Parent/lock, stage2 file owner and download reader. Wire binding occurs before
its first source query or ordinary input. No old live owner is adopted.

Prefix3 keeps its original host/epoch 120-second anchor. Upload keeps one
20-second action anchor, native queries keep their five-second operations,
source acquisition retains its original 1.5-second fences, and cleanup keeps
its original three-second quiet period and maximum 500-ms observation gap.
The same Parent bills every child, source copy, pending reservation and archive
against 512 frames, 16 MiB, and a 64-KiB control root. No reader or namespace
starts another allowance. These protocol byte limits do not bound Python RSS.

The original native body limit remains 4 MiB. Layout2 explicitly reuses the
existing Audio range/index journal with its pinned 4-MiB profile; default Audio
callers remain at 1 MiB. One range token and an independently pre-reserved
lossless tail bundle retain a whole wire of at most 4 MiB plus 4096 bytes of
framing/overrun probe. A malformed wire remains an opaque original. A valid
wire receives a distinct nonce/body-extent/SHA view, which is checked again
when existing native JSON readers consume the body. It is not another raw
copy or a decoder verdict cache.

The ordinary Stage command is 37,208 bytes, or 37,209 bytes including its
newline. The existing generic SDK writer's 16-KiB cap refuses it. The opt-in
Assets writer instead sends the same closed command through the original SDK
binary stdin method, with a fixed package/path and a 61,440-byte Stage cap.
The remote script retains an opened file through atomic rename and checks
actual byte extent, hash, process birth, and file metadata. Its separate
transport receipt is a pre-reserved SourceBundle original of at most 4096
bytes; it does not prove a native file lease or an upload. The original native
response reservation remains pending throughout. Unknown write/receipt
success cannot replay Stage.

Both ordinary and partial-timeout SDK returns enter original storage before
UTF8, framing, JSON, or receipt validation. The existing Uploads capture runs
exactly once above a cold-only raw-reader binding. A warm/pending/previously
captured reader cannot replace that callback. Final current-file windows run
after the original ScriptSourceLock exit without reacquiring that lock; they
check original directory/writer OFDs and fresh complete root/index/range
bytes and stamps against the same admitted pins. Uncertain owners remain held.

## Independent backend direction

The passive native instrumentation is gated by E2E, Linux, and exact runtime
`OVERTE_E2E_PICO_ASSETS_ORIGINALS_ENABLE=1`, with an explicitly configured,
canonical, owned private output directory. Disabled instrumentation starts no
snapshot timer or blob scan. Non-E2E product bodies remain unchanged.

The producer records actual task/process lifetimes and bounded mapping/blob
snapshots on their owning threads. Original weak NodeList bookends prevent
one capture from accepting a destroyed or replaced NodeList. Captures remain
periodic committed source observations, not socket receipts or caller-requested
results. File publication uses original descriptor pairs and a pending marker;
unsupported runtime OFD queries refuse admission, including when the NDK omits
the Linux query macro and the exact Linux command number is used instead.
Target kernel support remains unverified.

The host reader requires an already existing configured process, original
PID/start/executable authority, actual original directory/file OFDs, bounded
fresh reads, and raw retention before decoding. Its same-PID/instance/domain
continuity, pending-write refusal, process-loss and foreign-holder failures
are sticky. It does not start or discover a server, oven, gateway or Domain.
A remote Raspberry Pi backend still requires an authorized original-evidence
transport running on its host; a local `/proc` reader is not that transport.
No HTTP service or permanent Domain was provisioned by this packet.

Upload responsibility joins the actual selected file bytes/filenames, native
upload/mapping observations, independent backend originals and actual hash
response bytes. An ACK or requested destination cannot stand in for those
observations. Consumer/file cleanup retains original ownership on any failure;
quiet failure cannot authorize deletion.
