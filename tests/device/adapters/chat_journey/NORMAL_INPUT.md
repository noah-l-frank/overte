# Original normal Chat input owner

`ChatNormalInput` records one closed ordinary input attempt before any input or
query. It uses the existing `TokenChatUI`, which Pico binds to its original
installed-candidate, process and OpenXR-owned controls. Normal CHAT entry,
Unicode typing, Local/Domain tabs, Send or Return, and normal BACK remain product
inputs. A hidden tablet opens through the existing `PicoNavigation.open` owner
and original controller gesture, with a distinct persisted controller-open intent
before dispatch. It is not a predicted QML command sequence or a direct page
setter. An uncertain gesture cannot be retried in the same recipe; a new owner
also refuses an interrupted overall attempt.

Both separately owned original `ChatSamples` roles acquire their own native
primary/peer/view/lifecycle sources. Input consumption and editor clearing never
supply delivery. Send requires exactly one new original primary arrival from the
actual primary self identity, a newly accepted matching stored row and, when a
mixer exists, exactly one independently observed remote peer arrival. Channel,
text, original receive times after the corresponding native baseline and
localOnly are checked. Offline Send requires actual native localOnly true,
unchanged actual peer reception and three seconds of fresh sources without
replay. The independent original editor must really clear; Return's actual
retained focus/keyboard are measured rather than invented.

Open/type/channel/close preserve original reception and storage histories.
Typing requires the real measured entity keyboard and actual editor focus.
Close cancels the actual draft and verifies no remaining focus/keyboard through
three seconds on both the actual host clock and all eight original source
clocks. Every quiet capture advances; gaps stay at most 1.5 seconds. The complete
actual Chat state and native arrival lists remain unchanged. Histories preserve
order and multiplicity: the explicit normal Retry after fresh mixer recovery
and the existing no-replay window adds a second local retry but only one actual
remote retry. No timer or successful HTTP/input receipt sends that second input.

Each distinct operation gets a bounded 20-second budget. Each source pair and
final guard/persistence stays within 1.5 seconds, including original wall clocks
read after final guards. Captured raw transition frames never become current
facts; convergence always requires NEW strict full queries from both roles.
Version 2 stores each completed original attempt once in the existing private
`ChatSourceChunks`; the root keeps its immutable manifest and only the current
attempt in the existing compressed-history codec. This bounds each packet
without dropping any original quiet captures or increasing the 48 KiB limit.
Before sealing an attempt the root durably enters `reading`; lost root/child
writes and orphan chunks refuse reconstruction and further input. No original
chunk is overwritten, retimed, replayed or removed. Version 1 is retained
without adoption. The owner stores only original source references and actual
input intents,
validates the historical closure/quiet proofs on reconstruction, and never
queries or inputs during reconstruction. A repeated ticket or any interrupted
attempt refuses further inputs. There is no resend, transcript reset or owner
retirement API. The original source and input files remain even on success.

The Pico `_chat_normal_input` factory pins the actual candidate and distinct
role journal paths. Base teardown refuses green while this input owner remains.
Focused host tests use declared synthetic widget/native/peer boundaries and the
actual token/Pico/owner code. They cover button and Return routes, cancelled
draft, hidden tablet, genuine local-only fallback, independent remote receipt,
missing/false ACK effects, stale original receive time, late final clocks,
explicit retry multiplicity and once-only lost-input handling. No Overte
executable, service, headset, device or actual networking was run. Full Chat
capability remains closed pending whole-journey/publisher/lifecycle/profile/
resource/process-retirement composition.
