# Explicit iOS terminal retirement profile

The unchanged default v16 journey requires an empty resource inventory during
its live cleanup window. The optional `ios-native-process-end-v1` profile adds
`feature.<area>.terminal` with its own version 1. Advertising that capability
selects the profile in the existing catalog module, OverteSession and adapter
operation path. No adapter advertises it merely because the codec exists.

Some ordinary iOS controls hide a process-owned Qt root without destroying it.
Cached QSG roots, QImages and WK/native holders can likewise outlive a restored
scene. Those actual held lifetimes must remain explicit in public resources;
they cannot be reported as an empty native inventory before process exit.

The profile has three closed stages:

1. After both ordinary cleanup calls, `inspect` returns the original run/ticket,
   both qualified candidate/process/session-hash bindings and exact held native
   resources. Each resource has a bounded public `panel:` alias, one closed
   native class and its private original hash. This does not permit retained
   files, entities, active timers, inputs or pending callbacks to be hidden as
   cached objects. A feature decoder must establish their real cleanup first.
2. The existing engine still requires repeated fresh restored primary facts
   and independent actor facts for at least three seconds. Every primary sample
   must enumerate exactly the inspected held resources. `seal` receives these
   actual observations, not expected checkpoints. The feature decoder must
   reopen its own original source/image/input histories and independent actor
   retirement receipt, validate native quiet windows excluding boundary reads,
   and match the received observations to those originals. Its durable seal
   pins the exact paired window, held-owner description and full live proof.
3. Only after that seal, the module retires its owned fixture. `finish` validates
   the actual retired authority and original seal before its ordinary Stop.
   Each role uses its own admitted existing SDK and OS/DVT numeric-PID source
   to prove the old PID and bundle absent over at least three seconds. Source
   clocks remain Appium Node-host clocks; they are never labelled native time.
   Actual immutable archives, once-Stop receipts and canonical SDK deletion
   originals remain bound to the same held-owner originals. Logical observers
   sharing a session must reference the same one Stop and one SDK deletion.

The process-end result contains no live feature state, image or invented zero
native inventory. The engine makes no live observation after `finish`. A green
journey requires a validated complete terminal result within its separate
30-second limit. This new final stage changes no existing action, observation,
publication or freshness deadline. An uncertain seal, fixture retirement or
Stop result causes failure; the engine does not repeat that operation. The
feature owner must retain its durable unresolved responsibility for recovery.

Hashes and codecs prove binding and grammar only. They cannot establish
restoration, native lifetime drainage, PID absence or SDK deletion. An iOS
adapter must implement and test its full historical source-to-seal and
source-to-process-end decoders before advertising this optional capability or
its whole feature. The terminal response must match its actual durable seal;
caller-supplied observations cannot create measurement authority.

The six protocol contracts write/read version 1. Default v16 operation inputs,
observation/result shapes, scenario inventory and zero-resource cleanup remain
unchanged. The host tests run the actual common journey against an independent
reducer and explicitly modeled native/OS/SDK boundaries. They check retained
root visibility, both ordinary cleanup calls, paired stability, stage ordering,
changed/replayed/foreign observations, uncertain delivery, short/wrong PID
proofs and duplicate deletion claims. They establish no iOS native compilation
or device result. The complete iOS finalizers remain separate required work.
